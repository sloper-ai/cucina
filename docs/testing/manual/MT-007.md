# MT-007: Fresh production install on EKS using only the README

The acceptance campaign deploys to a throwaway k3s cluster. Production is EKS, which is documented but never deployed by the campaign. This check is a documentation test as much as a
product test: someone who did not write the docs follows the README and the guides it links, and only those, to a working install.

## Preconditions

- A person who did not write the documentation, and who agrees to use no other source (no asking the authors, no searching the code).
- A new EKS cluster in a fresh test account or VPC (version supported by the chart), with the EBS CSI driver and either EKS Pod Identity or IRSA available, a DNS name, and a TLS plan.
- AWS access for the tester sufficient to create the pool prerequisites; Packer and the image prerequisites installed as the docs describe.
- A stopwatch and a place to log every stumble.
- Evidence rules: [`README.md`](README.md#evidence). Use placeholders for account IDs, addresses and names.

## Steps

1. [human] Starting from the top-level `README.md` only, follow the quickstart and the linked EKS guide ([`docs/operations/eks.md`](../../operations/eks.md)) to a working install. Start the stopwatch. Every time you have to guess, search elsewhere or ask, write it down with the page and section: each is a documentation defect.
2. [human] Configure AWS access for the controller with Pod Identity or IRSA, and the storage class for the storage volumes (raw block volumes on the EBS CSI driver), as the guide says.
3. [human] Build the Linux worker image and configure a Linux pool from the docs ([`docs/operations/images.md`](../../operations/images.md)).
4. [agent] Install and verify: `helm install` as documented, `helm test`, `cucinactl status`.
5. [human] Log in with the break-glass key, add a `TrustPolicy` for your identity provider and log in through it, then **revoke** the break-glass key as the docs describe (`cucinactl keys revoke <key id>`): setting `auth.breakGlass.enabled=false` alone does not stop a key that was already issued. Confirm that logging in with the revoked key now fails.
6. [human] Run a first remote build through the cluster. Stop the stopwatch; record the time from the first command to the first successful remote build.
7. [agent] Verify the zero-idle claim with the pool idle: a tag-filtered describe of the cluster's instances in all non-terminated states (`aws ec2 describe-instances --filters Name=tag:cucina:cluster,Values=<cluster> Name=instance-state-name,Values=pending,running,stopping,stopped`), of volumes and of network interfaces returns nothing.
8. [agent] Check the storage volumes: `kubectl -n <ns> get pvc` shows the expected storage class and volume mode (`data-*` claims in file mode; `meta-*` and `cas-*` in block mode), and `cucinactl status` is healthy. Retention cannot be judged on a fresh cache (the metric reads unbounded until the first eviction), so compare the configured CAS size with the [sizing guide](../../sizing.md) for the expected daily writes instead.
9. [agent] Uninstall as documented (`helm uninstall`, allow the documented timeout). Confirm no worker instances, volumes or network interfaces remain.

## Expected results

- The tester reaches a working install and a first remote build using only the README and the pages it links.
- The idle cluster has no worker resources; storage uses the documented class; uninstall leaves nothing behind.
- Every place the tester had to leave the docs is recorded and becomes a documentation fix.

## Required evidence

- The list of documentation defects (page, section, what was missing) and the issues opened for them.
- The elapsed time from step 1 to step 6.
- Transcripts of steps 4, 7, 8 and 9 with identifiers redacted.
