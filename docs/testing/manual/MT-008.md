# MT-008: Disaster drill, storage loss and cold-cache recovery

The cache is reconstructible and is not backed up. This drill proves it: destroy the storage volumes of a non-production deployment and measure how long recovery takes and what the user sees.
Destructive: run it only on a staging deployment.

## Preconditions

- A staging deployment with a warm cache for a reference build (for example the Abseil build used by the campaign) and the remote repository contents cache seeded.
- Reference timings for that build: cold (empty cache) and warm (all cached), and the baseline retention and hit-rate metrics.
- Cluster admin access and permission to delete PVCs in that namespace. Read the [storage loss runbook](../../operations/storage-loss.md) first.
- Evidence rules: [`README.md`](README.md#evidence).

## Steps

1. [agent] Record the baseline: a warm build's wall time, remote cache hit rate and bytes transferred, the CAS retention metric, and `cucinactl status`.
2. [human] Start a long build (a repeat of the reference build with a few minutes of work remaining) so that a client is mid-build when the storage disappears.
3. [human] Destroy the storage: scale the storage StatefulSet to zero, delete its PersistentVolumeClaims, scale it back up so that empty volumes are created (the exact commands are in the runbook, in the variant that starts every shard clean).
4. [agent] Observe the control plane: storage pods start with empty state, `helm test` passes, and the cache canary succeeds; the cache hit-rate alerts fire once traffic runs against the empty cache (they need 30 minutes), but the retention alerts do not, because retention reads unbounded until the first eviction. Record the time to a healthy control plane.
5. [agent] The mid-build client from step 2 finishes without failing (it retries lost inputs; `--experimental_remote_cache_eviction_retries` and rewinding apply). Record any error it showed.
6. [agent] From a fresh client output base, run the reference build. It is a cold build: record wall time, cache hits (near zero) and bytes. Compare to the cold reference.
7. [agent] Repeat the build: it should now be at least 99 % cache hits. Record the time until the cache is warm again.
8. [agent] Check the repository contents cache. If the trusted writer has not re-seeded it, record the extra external-repository bytes a fresh client downloads, then re-seed it (CI on `main`) and confirm the download drops.
9. [human] Confirm workers need no manual action: their L1 caches refill from the new L3 and no worker restarted.
10. [human] Write the measured numbers into the [storage loss runbook](../../operations/storage-loss.md) and open an issue for anything that surprised you.

## Expected results

- No client build fails; builds slow down until the cache refills.
- Recovery needs no manual repair beyond recreating the volumes.
- The cold-cache build time is close to the reference cold time, and the second build is at least 99 % cached.
- The cache hit-rate alerts fire for the lost cache and clear as it refills; the retention alerts stay quiet (retention is unbounded until a store has evicted for the first time).

## Required evidence

- A recovery table: time to healthy control plane, time to the first successful cold build, time to a warm cache (at least 99 % hits).
- Cache-hit graphs or queries for the period (and the retention query, which reads unbounded after the drill until the first eviction).
- The mid-build client's output.
- The updated runbook numbers.
