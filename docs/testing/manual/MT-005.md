# MT-005: macOS and Xcode upgrade

Proves the two upgrade procedures an operator repeats most: updating a host's macOS (drain, update, uncordon) and adopting a new Xcode in the guest image (build, smoke test, roll out by
generation) with the old Xcode still serving builds.

## Preconditions

- An enrolled host with an idle macOS pool, a second host or pool is helpful but not required.
- A new macOS release available to the host (through the MDM's software-update declaration or manually) and a new Xcode version (a Cirrus image for it, or a `.xip` and the operator's Apple ID).
- The image build tooling (`workers/macos`) and registry access, and a Bazel project that selects an Xcode version through the generated platforms.
- Read the runbooks first: [macOS update](../../operations/macos-update.md) and [new Xcode, Visual Studio or OS release](../../operations/new-xcode-vs-os-release.md).
- Evidence rules: [`README.md`](README.md#evidence).

## Steps

1. [agent] Record the baseline: `cucinactl hosts list`, `cucinactl images`, `sw_vers` on the host, and `xcodebuild -version` from a build on the current image.
2. [agent] Drain the host: `cucinactl hosts drain <serial>`. Wait until `cucinactl hosts list` shows no running VMs for it (running actions finish first).
3. [human] Update macOS on the host, through the MDM's declaration in its maintenance window or by hand in System Settings. The host reboots.
4. [agent] The host reconnects (`cucinactl hosts list`: Offline, then Online) and reports the new macOS version.
5. [agent] Settings survived the update: `fdesetup status` is Off (macOS 26.4 and later may turn FileVault on in Setup Assistant), `pmset -g` is unchanged, auto-login still logs in `cucina` after a reboot, `sudo launchctl print system/ai.sloper.cucina.hostd` shows the daemon running, `sudo sfltool dumpbtm` still lists it.
6. [agent] Uncordon and use the host: `cucinactl hosts uncordon <serial>`, then run a macOS build. A VM starts on the updated host and the build passes.
7. [agent] Build the new guest image: `make -C workers/macos image-macos XCODE=<new version>`. It builds, runs its smoke test and reports the image version. `cucinactl images` lists it after publishing to the registry.
8. [human] If the new Xcode comes from a `.xip`, download it from Apple Developer with the operator's Apple ID. This step is manual and the credential is never stored anywhere.
9. [agent] Roll it out: add a pool or platform for the new `xcode-version` and apply it (`helm upgrade`; adding a platform restarts the scheduler, ADR 0002), or bump the existing pool's generation. `cucinactl pools describe <pool>` shows the new generation and the image resolved.
10. [agent] Run a remote build that selects the new Xcode version and confirm from the action's output that it ran on the new image (for example a genrule that prints `xcodebuild -version`).
11. [agent] The old Xcode pool still serves builds at the same time (side by side), and an idle old-generation VM is re-cloned at its next shutdown.
12. [agent] Roll back: point the pool at the previous image or generation, run a build, confirm it uses the old image.

## Expected results

- The host updates with no lost configuration and no manual repair; it is schedulable again after uncordon.
- A new Xcode is one scripted image build plus a generation bump, not a code change.
- Old and new versions coexist; rollback works.
- Hosts run a macOS version at least as new as their guests.

## Required evidence

- Version output before and after (`sw_vers`, `xcodebuild -version`, `cucinactl images`).
- The `fdesetup`, `pmset`, `launchctl` and `sfltool` checks from step 5.
- The image build log summary and smoke-test result.
- The build output from step 10 and the rollback build from step 12.
