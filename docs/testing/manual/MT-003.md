# MT-003: Real GitHub Actions OIDC run in `sloper-ai/cucina`

The automated tests use a mock issuer shaped like GitHub's. This check runs the real thing in this repository's own workflow: the job obtains a GitHub ID token, exchanges it
at the Cucina STS, builds through the deployment, and the trust policy gives write access to the action cache only to pushes to `main`. It also proves that forks and
`pull_request_target` workflows get nothing.

## Preconditions

- A Cucina deployment reachable from GitHub-hosted runners, with the `TrustPolicy` for this repository installed: `repository_owner_id` and `repository_id` pinned (never `sub`), event names allow-listed, `pull_request_target` denied, `ac-write` only for pushes to `refs/heads/main`.
- The repository variable `CUCINA_ENDPOINT` set, so the `rbe` job in `.github/workflows/ci.yml` runs, with `id-token: write` permission.
- A second GitHub account that can fork the repository, and a throwaway repository under the same owner for the wrong-repository test.
- Evidence rules: [`README.md`](README.md#evidence).

## Steps

1. [human] Push a trivial commit to a branch other than `main`. The `rbe` job runs: the credential helper requests a token with audience `cucina`, exchanges it, and `bazel test --config=cucina-ci //...` passes.
2. [agent] Find the STS audit line for that run. It shows a subject of the form `github:<repository id>:<workflow>`, the issuer, and the granted verbs: read and execute, **no** `ac-write`. It never shows a token.
3. [human] Push to `main` (or run the workflow manually on `main`). The job passes and now holds `ac-write`; the audit line shows it.
4. [agent] Confirm the main run wrote action-cache entries and the branch run did not (cache statistics, or a second run's hit counts).
5. [human] In a throwaway branch add a workflow triggered by `pull_request_target` that requests the OIDC token and tries to exchange it. The exchange must be denied.
6. [human] From the second account, fork the repository and open a pull request. The `rbe` job must not get write access: GitHub withholds the ID token from fork pull requests, so the job either does not run or fails closed. It never builds with write access.
7. [human] In the throwaway repository under the same owner, run a workflow that requests the `cucina` audience and exchanges the token. It must be denied (wrong `repository_id`).
8. [agent] Replay: send the same GitHub ID token to the STS twice (from a captured job step, within its lifetime). The second exchange is refused if the replay cache is enabled; record the behaviour either way.
9. [human] Run a build longer than 15 minutes in the workflow. The helper fetches a fresh GitHub token on each renewal and the build completes.

## Expected results

- A branch run can read and execute, not write the AC. A `main` push can write it.
- `pull_request_target`, forks and other repositories are denied.
- Audit lines exist for every exchange and contain no token values.
- Nothing is stored in GitHub secrets for this to work.

## Required evidence

- Links to the workflow runs for steps 1, 3, 5, 6, 7 and 9.
- The audit lines for steps 2 and 3 (subject, issuer, verbs, result).
- The cache statistics from step 4.
