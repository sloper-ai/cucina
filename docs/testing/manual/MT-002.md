# MT-002: Real Google Desktop-app login

The automated tests use a mock identity provider. This check uses the real Google endpoints, a real consent screen and a real browser, for the three ways a
developer logs in: the browser flow, `--manual`, and an SSH port forward. It also checks that offboarding at the identity provider takes effect within a token lifetime.

## Preconditions

- A Cucina deployment with a `TrustPolicy` for your Google Workspace domain (`hd` allow-list, `email_verified`) granting at least `execute` and `cas-read`.
- An OAuth client of type "Desktop app" in your Google Cloud project with an Internal consent screen, whose client ID and secret are published in the STS discovery document.
- Two test accounts: a Workspace user inside the domain, and an account outside it (for example a consumer account).
- A laptop with a browser, and a second machine reachable over SSH that has no browser.
- A Bazel project that can build through the deployment.
- Evidence rules: [`README.md`](README.md#evidence). Never paste a token, a refresh token or a key.

## Steps

1. [human] On the laptop run `cucinactl login https://<sts address>`. The browser opens on Google's consent screen and the URL is also printed. Sign in as the Workspace user and approve. The CLI reports success.
2. [agent] `cucinactl whoami` shows the principal as `google:<numeric sub>` (never the email address), the grants from the trust policy, and an expiry at most 15 minutes away.
3. [agent] The credential helper answers without prompting: `printf '{"uri":"https://<host>/build.bazel.remote.execution.v2.Execution"}' | cucinactl credential-helper get` prints a JSON document with an `Authorization` header and an RFC 3339 `expires` without fractional seconds. Do not keep the output.
4. [agent] Build through the deployment with the generated configuration (`cucinactl bazelrc --platform linux`): `bazelisk build //...` succeeds.
5. [human] Keep a build or test running for more than 15 minutes. It must finish without an authentication error (the helper renews with the stored refresh token).
6. [human] Log out (`cucinactl logout`), then try the account outside the domain: `cucinactl login https://<sts address>`. Login must fail with a clear message, and the STS audit log must show a rejection with no token material.
7. [human] **Manual path**: on the machine without a browser, run `cucinactl login https://<sts address> --manual`. Open the printed URL in the laptop's browser, approve, copy the address the browser ends on (it will not load), and paste it into the prompt. Login completes. A pasted address with a wrong `state` is rejected.
8. [human] **SSH-forward path**: from the laptop run `ssh -L 127.0.0.1:<port>:127.0.0.1:<port> <host>`. On the host run `cucinactl login https://<sts address> --port <port> --no-browser`, open the printed URL in the laptop's browser, approve. Login completes on the host.
9. [human] **Offboarding**: log in as the Workspace user, then suspend that user in the Google Admin console. Within one token lifetime (15 minutes) `cucinactl whoami` and the credential helper must stop working (exit code 3, "run `cucinactl login`"), and a Bazel build must fail with that message.
10. [human] Restore the user. Revoke the app's access in the Google account's third-party access page. The next renewal must fail the same way.
11. [agent] `cucinactl logout`, then `cucinactl whoami` exits with code 3, and no Cucina entry remains in the OS keychain.

## Expected results

- All three login paths work with real Google, and the principal is keyed on `sub`, never on the email.
- A user outside the allowed domain cannot log in; the rejection is explained and audited.
- A build longer than one token lifetime renews transparently.
- Offboarding at the identity provider takes effect within 15 minutes; revoking the grant takes effect at the next renewal.
- Tokens, refresh tokens and keys never appear on screen or in logs beyond what the tool prints by design.

## Required evidence

- Transcripts of steps 2, 3 (without the header value), 7, 8, 9 and 11, with identifiers redacted.
- Timestamps of the suspension (step 9) and of the first failure.
- The STS audit lines for steps 1, 6 and 9 (subject and result only).
- Screenshots of the consent screen with account names blurred.
